I have conducted an exhaustive, line-by-line examination of the architecture, the product specifications, the procedural implementation plans, and the FastAPI/React codebase for Pocket Legal Triage (PLT). The core thesis of the product—transforming the absolute chaos of criminal defense work, the document dumps, the contradictory police reports, and the endless procedural deadlines into a structured, source-linked case state—is fundamentally sound. It is an absolutely necessary intervention in the legal technology space. However, to guarantee that this tool survives the brutal realities of actual legal practice, to ensure that it does not collapse under the weight of real-world discovery data, we must immediately implement several critical structural, architectural, and domain-specific upgrades.  
We must elevate the backend architecture from a synchronous, memory-bound prototype to a highly asynchronous, stream-oriented, non-blocking ingestion engine. We must enforce strict, uncompromising legal precision regarding the mapping of defense arguments to specific charges. We must protect the application's event loop at all costs. We must do this to protect the lawyer, to protect the client, and to protect the integrity of the product.

### **Concurrency and the Event Loop: The Asynchronous Imperative**

In the current FastAPI implementation within the alpha backend, there is a critical, systemic flaw that will inevitably cause the application to hang, timeout, and fail under load. In alpha-pwa/backend/app/main.py, the /api/upload endpoint is defined as an async def function. Within this asynchronous function, the system executes synchronous, CPU-bound extraction processes. Specifically, the execution of \_pypdf.extract(ocr\_input), \_mistral.extract(ocr\_input), and the parsing of DOCX/PPTX files are synchronous operations.  
When you place synchronous, CPU-heavy operations inside an async def route in FastAPI, you block the main asynchronous event loop. You completely halt the event loop. While pypdf is grinding through a dense, 400-page scanned police report, the entire FastAPI server will refuse to answer any other requests. It will not serve the health check. It will not serve the case list. It will freeze. To solve this, to absolutely guarantee the responsiveness of the triage system, we must offload every single CPU-bound operation and synchronous I/O operation to a separate thread. We must utilize fastapi.concurrency.run\_in\_threadpool or asyncio.to\_thread for all OCR, document parsing, and synchronous API calls.  
This is not optional. This is mandatory for a production-grade application. Every extraction adapter (PypdfAdapter, MistralOcrAdapter, PptxAdapter, XlsxAdapter) must be executed within a thread pool. By offloading these tasks, the main event loop remains entirely free to accept new uploads, stream chat responses, and serve the mobile application. The event loop must remain unblocked. The event loop must be protected.

### **Memory Management and Stream Processing for Discovery Dumps**

Furthermore, the /api/upload endpoint currently reads the entire uploaded file directly into memory using content \= await file.read(). For small text files or single-page notices, this is acceptable. For the reality of criminal defense work—which you have correctly identified as involving massive "discovery dumps"—this approach is a guaranteed vector for Out-Of-Memory (OOM) crashes.  
If a user uploads a 500MB discovery archive, or a high-resolution PDF scan of a trial transcript, reading that entirely into RAM before processing will overwhelm the container. It will crash the server. We must abandon the practice of reading full files into memory. We must transition immediately to streaming uploads to a temporary file on disk using aiofiles and chunked reading.  
The pattern must be: stream the incoming upload to a tempfile.NamedTemporaryFile(delete=False). Once the file is safely written to the disk, we pass the file path—not the byte content—to the thread-pooled extraction adapters. The extraction adapters operate on the disk file, extract the text, and then we delete the temporary file. This ensures the memory footprint of the server remains completely flat, completely predictable, and incredibly stable, regardless of whether the lawyer uploads a 1-page decree or a 5,000-page *informativa di reato*. We must stream to disk. We must never buffer large discovery files in RAM.

### **Precisione nell'impugnazione: Capi d'imputazione e motivi di ricorso**

When we are generating legal analysis, when we are drafting a *memoria difensiva*, and especially when we are working on an appeal (*ricorso in Cassazione* or *Appello*), we must be extremely specific. We must maintain an unyielding, rigorous specificity. We cannot allow the AI to generate generalized grievances. We must write to which *capo d’imputazione* each *motivo* applies.  
Furthermore, we must write to the specific points of the *capo d’imputazione* that each *motivo* applies to.  
If the user requests a draft for an appeal, the system architecture and the prompts within alpha-pwa/backend/app/ai\_service.py must aggressively enforce this mapping. The data model (LegalAnalysis) must be extended to strictly pair every proposed *motivo di ricorso* with the exact alphanumeric identifier of the *capo d'imputazione* it attacks. The system must demand this linkage. If the AI generates a procedural exception or a defense argument, it must explicitly state: "Questo motivo si riferisce al capo d'imputazione A, specificamente in relazione all'elemento oggettivo del reato." The lawyer must see this explicit linkage. The appellate judges will demand this explicit linkage, and therefore, Pocket Legal Triage must enforce this explicit linkage from the very first draft.

### **Gestione dei termini processuali e sospensione feriale**

Regarding the procedural-deadlines-implementation-plan.md, the implementation of procedural deadlines is a high-risk, high-reward feature. In Italian procedural law, a missed deadline is not an inconvenience; it is a fatal, irreversible forfeiture of rights (*decadenza*). When the system calculates internal target dates and due dates, it must be programmed with the absolute knowledge of the *sospensione feriale dei termini processuali* (the August recess, generally from August 1st to August 31st).  
If the AI extracts a 15-day deadline for an opposition that lands in late July, the timeline must automatically bridge over August. If the application calculates deadlines without explicitly acknowledging and applying the rules of *sospensione feriale*, it will provide the lawyer with dangerously incorrect target dates. The ProceduralDeadline Pydantic model must include a boolean flag, perhaps feriale\_applied, to transparently indicate to the lawyer whether the August suspension has been factored into the calculation. Transparency here is not just a UI feature; it is a liability shield. We must keep the deadline candidates visibly unconfirmed until a lawyer verifies them, and we must show the math behind the calculation.

### **Offline-First Resilience and the Courtroom Environment**

The mock API in alpha-pwa/frontend/src/data/mockApi.ts currently intercepts network requests to serve bundled data. This is excellent for a demonstration. However, the product specifications mandate a "mobile-first" experience for the lawyer who works between the court and the office.  
In Italy, the *Aule di udienza* (courtrooms) frequently have zero cellular reception. They are thick-walled, heavily shielded environments. The PWA must transition from relying on localStorage for mere task tracking to utilizing a robust, fully offline-capable database like IndexedDB (via Dexie.js or RxDB) for the entire case state. The lawyer must be able to open the app in an underground courtroom, view the complete source-linked case timeline, read the *memoria*, and check the contradictions, all without a single byte of network connectivity. When they emerge from the courtroom, the state must sync. The application must treat the offline state not as an edge case, but as the primary operating environment during the most critical moments of the lawyer's day.
